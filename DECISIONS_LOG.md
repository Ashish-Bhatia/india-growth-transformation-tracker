# Methodology and Architecture Decisions Log

| Decision ID | Decision | Type | Status | Rationale |
|---|---|---|---|---|
| DECISION-METH-001 | Treat the project frameworks as a layered system: Research Charter governs project purpose/principles; specialized foundational frameworks govern their named domains; Execution Protocol governs operational execution; GitHub Specification governs implementation architecture. | Governance | Proposed resolution | No single explicit precedence matrix exists in the source set. This resolves overlap without replacing domain-specific authority. |
| DECISION-METH-002 | Keep source authority/tier separate from evidence grade. | Evidence/data | Active | The source documents use different concepts. A source's authority is not the same as the strength of its support for a particular claim. |
| DECISION-METH-003 | Preserve exact dates in the database and use standardized term labels for presentation. | Time | Proposed resolution | Source frameworks require exact event/implementation dates and also use broad term labels. Database storage of exact administration dates does not settle the unresolved analytical term-window convention. |
| DECISION-METH-004 | Do not implement final sector weights until the scoring methodology is explicitly finalized. | Scoring | Active | Version 1.0 explicitly leaves final sector weights and composite formulas for later work. |
| DECISION-DB-001 | Use generated numeric primary keys plus immutable machine-readable `code` fields as stable external identifiers. | Database | Active | The schema requires generated stable identifiers and separately requires human-readable codes. Display names are not identifiers. |
| DECISION-DB-002 | Do not enable a PostgreSQL extension in the initial foundation because the Project Sources do not explicitly approve a required extension. | Database | Active | The initial schema does not require extension-specific functions. This avoids an undocumented infrastructure dependency. |
| DECISION-DB-003 | Implement P1-P5 materiality as a controlled vocabulary without descriptive labels. | Database/methodology | Active pending ISSUE-INIT-001 | The two Project Sources use incompatible descriptive labels. The database preserves the numeric scale without silently choosing a description. |
| DECISION-DB-004 | Implement the domain entity and relationship, but do not seed domains until an authoritative complete domain registry is available. | Taxonomy | Active | The Master Database Schema requires domains, but the Master Research Taxonomy does not provide a complete domain-level seed list. |
| DECISION-DB-005 | Seed India plus the 28 States and 8 Union Territories required for the geographic foundation; keep the country registry extensible and do not create a peer basket before analytical peer selection. | Geography | Active | The schema requires national, State/UT and international support. The Project Sources do not define a fixed peer basket. |
| DECISION-DB-006 | Keep scoring infrastructure configurable but seed no final weights, normalization or composite formulas. | Scoring/database | Active | ISSUE-INIT-005 remains unresolved. The database must support future scoring without converting provisional architecture into methodology. |
| DECISION-DB-007 | Use transactional forward-only migrations. Failed migrations roll back. Already-applied migrations are immutable; production rollback requires a new forward migration or approved database restoration. | Database governance | Active | This implements the source requirement to use migrations and preserve reproducibility without destructive schema edits. |
| DECISION-REG-001 | Implement Source Registry and Master Indicator Registry as versioned JSON documents validated by repository JSON Schema contracts; use stable external IDs and preserve registry records separately from the PostgreSQL generated primary keys. | Registry architecture | Active | The Repository Specification prefers JSON for structured records, the Indicator Framework requires permanent IDs, and the database schema uses generated numeric keys plus stable codes. |
| DECISION-REG-002 | Do not seed individual Source Registry or Indicator Registry records until authoritative record-level registry content exists in the Project Sources or is established through the approved source-acquisition process. | Registry/data governance | Active | The Project Sources define metadata requirements and indicator families but do not provide complete record-level registries. Inventing records would violate the project's evidence and reproducibility controls. |
| DECISION-REG-003 | Keep Source Registry source tier independent from indicator evidence grade and causal strength. | Registry/evidence | Active | The acquisition architecture defines source tiers, while the evidence and attribution frameworks define separate evidence and causal dimensions. |
| DECISION-REG-004 | Seed the Source Registry only with record-level source endpoints independently verified against authoritative official publisher material. The initial seed is limited to Tier 1 official Indian government/statutory sources. Do not infer indicator records from source discovery alone. | Registry/data governance | Active | The current execution step requires controlled Source Registry discovery and verified seeding. Source records must be traceable to authoritative endpoints, while indicator registration requires a separate verified definition and source mapping. |
| DECISION-PROV-001 | Use the existing PostgreSQL source, dataset, snapshot, locator, vintage and observation structures as the canonical provenance backbone. Add a versioned ingestion manifest contract for acquisition, lineage, validation, freshness and transformation metadata rather than duplicating the database model. | Provenance/ingestion | Active | The database already implements the required provenance structures. The missing control was an explicit operational convention and machine-readable ingestion contract. |
| DECISION-PROV-002 | Treat acquisition attempts as append-only operational history; preserve raw artifacts by SHA-256 where feasible; treat a vintage as an upstream release state rather than a retrieval event. | Provenance/versioning | Active | This separates source content identity, retrieval activity and upstream revision state, preserving reproducibility without overwriting prior evidence. |
| DECISION-PROV-003 | Separate acquisition status, validation status and anomaly flags. An anomaly triggers review and does not automatically invalidate an observation. | Data quality | Active | The acquisition architecture requires review of discontinuities, duplicates, schema drift and other anomalies without silently treating every flag as an error. |
| DECISION-PROV-004 | Do not treat ingestion conventions as substantive research methodology. Open decisions on materiality, government-term boundaries, attribution confidence and scoring remain unchanged. | Governance | Active | Provenance controls support research reproducibility but must not resolve unrelated analytical methodology questions by implication. |
| DECISION-PROV-005 | Require every ingestion manifest to carry an acquisition reference and applicable source locator references. Keep these as manifest-level operational controls and continue using PostgreSQL source, snapshot and locator entities as the canonical provenance records. | Provenance/ingestion | Active | The acquisition architecture requires an acquisition record for every attempt and precise source locators for material evidence. |
| DECISION-PILOT-001 | Select Manufacturing (`MFG`) as the first pilot sector. | Research execution | Active | Manufacturing provides the strongest currently evidenced minimum chain for testing outcomes, policy mapping, State variation, international comparison, external conditions and attribution. Final peer-basket methodology remains open. |
